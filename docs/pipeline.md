# SureJack 流水线全流程

从一段小说原文到一条可下载的成片，中间经过哪些步骤、每一步谁触发、
产出什么、失败了会怎样。**这份文档描述的是代码当前的实际行为**，
不是设计意图——两者不一致时以代码为准，并且请顺手改这里。

---

## 一、总览

```
贴文案
  └─▸ 人名分析（LLM）────────────┐
        └─▸ 确认替换表           │ 都在【配音之前】：
              └─▸ 确定性替换 + 去章节 │ 这几步改的是文案本身
                    └─▸ 清理复查（LLM）
                          └─▸ 标点体检（仅异常时调 LLM）
                                └─▸ 【可选】分集（LLM 给断点）
                                      └─▸ 定标题 / 水印文字
                                            └─▸ 挂起：开头待挑
                                                  ▼
                                            配音（Azure）
                                            ├─ voice.mp3
                                            └─ 词级时间戳 ──▸ 字幕语义切分（LLM）
                                                  ▼
                                            挑开头素材 ← 闸门，人不点就不往下走
                                                  ▼
                                            背景轨 bg-track.mp4（三段式排布）
                                                  ▼
                                            母带 master.mp4（ffmpeg 烧 ASS）
                                                  ▼
                                            混 BGM ──▸ 接封面两帧 ──▸ export.mp4
```

一条 10 分钟的片子，配音约 2–4 分钟，烧录约 12–15 分钟，其余各步都在秒级。

## 二、配音之前：文案怎么变成"能念的文本"

这一段的所有步骤都在改 `projects.script_text`。**一旦开始配音就不能再改**——
配音是照着这份文本念的，改了字幕就和耳朵对不上。

### 1. 人名分析（LLM ①）

`src/rename/deepseek.ts` · `analyzeNovel()`

把全文发给 DeepSeek，要它给出**替换映射**（顾文渊 → 顾闻缘）和人物关系。

- **铁律：LLM 只出映射，替换由代码执行**（`applyRename`）。让模型直接返回
  改写后的正文，等于把一万字的原文交给它重打一遍，它会顺手改别的。
- 逐字校验：姓保留、名字里每个字都必须换成**读音相同的另一个字**。
  没换干净就带着"哪几个字没换"重试，最多两次。
- 超时 120 秒；**偶发失败（超时/网络/5xx）再重试一次**——这和"名字没改干净"
  是两类重试，前者是压根没答上来，后者是答得不对。

### 2. 确定性替换 + 去章节

`src/rename/replace.ts`

按映射表逐字替换；按规则删掉章节标题行。纯函数，可复现。

### 3. 清理复查（LLM ②）

`src/rename/deepseek.ts` · `reviewCleanup()`

捞第一层漏掉的非正文，尤其是**孤立的数字行**那种只有语义能判、字符规则
抓不到的。同样是"LLM 出指令、代码删"。**失败不阻塞**，沿用第一层结果。

### 4. 标点体检（LLM ③，仅在异常时）

`src/importers/punctuate.ts`

这条流水线上**断句全靠原文自带的标点**：配音的停顿、字幕的断行、分集的
切句，三处都吃它。实测一篇正常网文 5790 字有 601 个标点（每 10 字一个）。

- **判据**：每 25 个字还不到一个标点才算异常；少于 200 字的一律算健康。
  阈值定得松是有依据的——正常文本离 25 很远，定太严会把文风紧凑的正常
  文本误判，白花一次调用还冒被改写的风险。
- **健康就一次 API 都不调。**
- ⚠️ **只能加标点**：把结果里的标点全剥掉，必须和原文逐字相同，否则整篇
  作废、原样用旧文本。模型很容易顺手"润色"，而这里的文案是作者的作品。
- **它是为了配音，不是为了字幕**。字幕太长有它自己的解法（第 7 节），
  不需要为了字幕好看去动声音。

### 5. 分集（可选，LLM ④）

`src/episodes/`

一条长文拆成主片 + 续集：

- **断点**：主片讲到悬念处收尾。可选范围锁死在 **7–10 分钟**
  （`TARGET_MIN_MS` / `TARGET_MAX_MS`），模型在范围内给几个候选并说明理由，
  用户滚轮选句子，**服务端也校验范围**——越界的断点会产出"12 秒的主片 +
  装着全文的续集"，而配音烧录封面全都会照做，直到成片出来才发现。
- **引子**：续集开头重复主片的钩子几句。问模型的是"正文从第几句开始"，
  引子 = 那一句减一——比问"钩子的最后一句"稳，减法交给代码做。
- **提醒语**：「周周提醒你，<主片标题>第二集开始啦」，单独配音、有字幕。
- **时长估算**：按 `EPISODE_MS_PER_CHAR = 110` 算（实测值）。注意配音切段
  用的是另一个更保守的 196。
- 续集是**独立项目**，靠 `parent_project_id` 关联；UI 上像母文件夹。

### 6. 定标题 / 水印

`web/.../EpisodeTitles.tsx`

**封面标题**（缩略图那一帧）、**片内标题**（顶部常驻）、**水印文字**
（两集共用，默认「周周」）。这三样都会被逐帧烧进产物，所以位置就是
"按下生成之前的最后一屏"——生成之后再改，代价是整条重烧。

## 三、配音

`src/tts/azure.ts` · `synthesizeLong()`

- 长文案按 Azure 单次上限切段合成，再拼接音频、平移时间轴。
- 产出两样东西：`voice.mp3` 和**词级时间戳**（每个词的文本 / 起点 / 时长 /
  是不是标点）。**字幕的全部时间信息只有这一个来源。**
- 实测粒度：非标点事件里 56% 是 1 个字、37% 是 2 个字，最长 7 个字。
  所以"只能在词与词之间下刀"这条约束，实际上细到几乎等于字符级。
- 分集项目：主片配完，**服务端自己接着配续集**（串行，不并发）。放服务端
  而不是前端是因为前端那条路要求页面一直开着，而按下生成就切走是常态。
- 免费额度：Azure F0 每月 50 万字符，限速每 60 秒 20 次请求。

## 四、字幕语义切分（LLM ⑤）

`src/subtitles/cut-ai.ts` · `src/subtitles/segment.ts`

**只动显示，不动声音。** 存在的唯一理由是一行放不下 17 个字。

### 为什么是 17

81 号字、左右各留 60px 安全边距 → 可用 960px。实测
（`spikes/subtitle/line-width.py`）：

| 字数 | 墨迹宽度 | 左右余量 |
| --- | --- | --- |
| 16 | 900px | 90 / 92 |
| **17** | **959px** | **61 / 61** ← 正好铺满安全区 |
| 18 | 1014px | 33 / 34 |
| 19 | 1070px | 5 / 6 |
| 20 | 1080px | 0 ← 出界 |

### 送谁去切

**不是"切完还超限的行"**——机械切分本来就以 17 收口，那个集合恒为空，
整层 LLM 会永远不触发（绕了一轮才想明白）。

真正要切的是 **`overlongRuns`：两个标点之间超过 17 个字的段**。那些段
机械切法只能在"第 17 个字"处下刀，刀口落在哪儿纯看字数——
「大力出奇迹」被劈成「大力出 / 奇迹」就是这么来的。实测一篇 5790 字的
文案有 **13 段**这样的。

### 两层 + 三级回退

1. **第一层**给断点，2. **第二层**复查（成语被劈？碎片？还超限？）。
和人名替换同一个套路。

- 复查挂了 → 用第一层的（它已经过了逐字校验）
- 第一层挂了 → 回退机械切法
- **"AI 没答上来"绝不能变成"字幕烧不出来"**

### 硬约束

- **只给断点，不许改一个字**：拼回去必须和原句逐字相同，否则整条作废。
- **断点吸附到词边界**：词内部没有时间戳，切在词中间就没有时间可用。
  正中间时取靠后那条缝——规则本身不重要，**确定**才重要。
- **统一调用**：所有段编号后塞进一次请求，60 段一批。一个项目正常
  2 次调用（切 + 复查）。

### 长度按【屏幕上真正显示的字】算

渲染时 `hidePunctuation` 会把标点字形全去掉。按带标点的长度判超限，
会把本来放得下的行送去切——弹幕体小说里这种行成片出现：

```
原始词表：】 【人类和人鱼在一起不能孕育后代，  = 17 字
屏幕上：  人类和人鱼在一起不能孕育后代        = 14 字
```

## 五、挑开头素材（闸门）

`web/.../OpeningPicker.tsx` · `POST /api/projects/:id/opening`

配音完成后不直接烧录，先停在这一屏让作者挑开头。

- **它是闸门，不只是一屏界面**：配音一完成服务端本来就会排队烧录，
  不拦住的话用户还在挑，片子已经拿着随机开头烧完了。闸门放了**两道**——
  配音完不入队、`resolveFilm` 也返回 blocked，因为开机补合走的是后者。
- **目标时长 = 配音总长 × 27%**，配音没跑完时不显示进度条也不设限
  （那时时长还是未知的，画一根按空值算的条等于给用户一个错的额度）。
- **铺满之后才封口**：跨过边界的那一段照样能加（截短正好铺满），
  铺满之后再加的才是纯粹用不上的，那时才拦并弹提示。
- **「用默认素材」不是"不选"**：后端会把默认排布**物化**成一份具体清单
  存库。排布本来是拿项目 id 当种子现算的，扫进新素材就会变；物化之后
  重烧多少次都还是这几段。
- **续集默认不与主片撞**：两集各用自己的种子洗牌，但抓的是同一个 68 段的
  桶，按概率平均会撞一段——所以排续集默认时**显式剔除**主片用过的段。
- 连着看一遍：双缓冲顺序播放，纯前端，不生成任何文件。

## 六、背景轨

`src/compose/plan.ts` · `src/library/background.ts`

三段式：**开头 27% / 常规 27% / 地铁跑酷 46%**，拼出一条与配音**精确等长**
的轨。续集换一套公式：几段开头（默认 5 段）+ 全程跑酷。

- 素材库三个桶：开头 68 个、常规 124 个、跑酷 9 个（GB 级长录屏）。
- 每个项目用不同组合、同一项目永远一致：拿项目 id 派生种子洗牌。
- **前两段用 floor、最后一段吃掉全部余数**，三段之和恒等于总长，
  一毫秒都不丢——四舍五入会让成片结尾黑一帧。

## 七、烧录

`src/render/` · `src/compose/film.ts`

一条 ffmpeg 命令把背景轨 + 配音 + ASS 烧成 `master.mp4`。ASS 里有四样东西：

| | 字号 | 描边 | 位置 | 颜色 |
| --- | --- | --- | --- | --- |
| 字幕 | 81 | 5 | 离底 999 | 黑字白边 |
| 片内标题 | 165 | 7 | 离顶 66 | 白字深灰边 |
| 免责声明 | 56 | 2 | 离底 19 | 白字黑边 |
| 水印 | 52 | 2 | 六角轮转 | 白字黑边，46% 不透明 |

全部是**逐像素拟合**用户给的参考图得来的（`spikes/subtitle/`），
误差 ≤2px；字体是仓库自带的思源黑体 Medium。

### 水印的轨迹

六个角：左上 → 右中 → 左下 → 右上 → 左中 → 右下，
到达时间 `0 / 1:30 / 3:00 / 6:00 / 9:00 / 12:00`，一轮 15 分钟。

- 段内**匀速滑动**（`\move`），实测 14.5 px/秒，四段之间差 0.03。
- 最后一段**停在右下不动**，到 15:00 那个溢出节点**瞬移**回左上。
  滑回去要横穿整个画面，而"回到原点"本身不是运动。
- 片尾截断时 `\move` 的时间参数仍写整段时长，否则水印会在最后几十秒
  加速冲刺。
- **时间表是绝对的**，不随片长缩放：4 分钟的片子只走到第三个位置。

### 之后

混 BGM（`mixed.mp4`，视频流 `-c copy` 不重编码）→ 前面接上**两帧封面**
→ `export.mp4`。封面的字号/位置也是拟合出来的。

## 八、指纹：什么会重烧，什么不会

`src/compose/film.ts`

两层指纹：

- **母带指纹** = 画幅 + 时长 + 背景排布 + ASS 全文哈希 + 配音路径
  （+ 偏离默认的配音参数 / 水印 / 字幕断点）。它变了 → 整条重烧（十几分钟）。
- **成片指纹** = 母带指纹 + BGM + 封面标题。只有它变 → 重混一次音（9 秒）。

实测同一条 10 分钟的片子：整条重烧 12 分钟，只重混音 9 秒——**80 倍**。

### carve-out：老片子绝不重烧

母带指纹哈希的是 ASS 全文，所以**样式行改一个字符、免责声明少一个逗号、
甚至加一行注释**，都会让所有历史项目的指纹失效、开机补合把它们全排上队。
用户明确要求过往不动，于是有了这套：

> **哈希用老配置，渲染用新配置。**

具体清单（每一条都是踩过之后加的）：

| 项 | 哈希侧用的值 |
| --- | --- |
| 字幕字数上限 | 14（渲染用 17） |
| 样式行 | `legacyStyleLines()`，含族名 `Noto Sans CJK SC` |
| 免责声明 | 带逗号的老版本 |
| 隐藏标点 | 关（渲染开） |
| 水印 | 不画 |
| 字幕语义断点 | 不用 |

后四项还有一个共同的写法：**只在偏离默认时才追加进指纹**
（配音参数、水印文字、字幕断点都是这样）。空值 → 数组和从前逐字节相同
→ 老项目指纹不变；一旦填了 → 指纹变 → 只有它自己重烧。

⚠️ **副作用**：有了这套 carve-out，**改样式再也不会触发任何重烧**，
连新项目也不会。要看新样式的效果，得手工删掉那条片子的产物。

## 九、队列与恢复

- **串行 FIFO**：进程内一个队列，不会一口气开一堆 ffmpeg。
- **开机补合**：服务启动时扫一遍所有项目，指纹对不上的排队重烧。
- **开机复位卡住的配音**：配音是十几分钟的长任务，状态先写 `generating`、
  跑完再写 `ready`。进程中途没了（部署重启、崩溃、OOM），那一行会永远停在
  `generating`，界面一直转圈而**根本没有任何进程在做这件事**。
  所以启动时把它们复位成 `error`，界面上显示"未完成"、有重试入口。
  **不自动重跑**——配音是唯一按量计费的一步，崩溃循环会在每次开机烧一遍配额。

## 十一、落在项目上的字段

除了文案、时间戳这些，和上面各步直接相关的：

```
rename_enabled / rename_state / rename_map_json / rename_analysis_json
parent_project_id / episode_index          分集
cover_title / in_video_title               两个标题
watermark_text                             水印（空 = 不打）
opening_pick_json / opening_state          挑开头（物化的清单 + 闸门）

subtitle_margin_v / subtitle_font_size     字幕位置和大小
voice_name / voice_rate / voice_volume / voice_pitch
```

新增列一律**默认空/老值**——`ALTER TABLE` 的默认值会回填进所有老行，
填一个非空值等于给历史项目凭空加上这个特性，它们的指纹随即失效。

## 十二、六处 LLM 调用点

| # | 用途 | 时机 | 失败了 |
| --- | --- | --- | --- |
| ① | 人名分析 | 点"分析人名" | 报错，可重试（自身已重试一次） |
| ② | 清理复查 | 确认替换表时 | 沿用第一层结果 |
| ③ | 标点修复 | 确认替换表时，**仅体检不过** | 原样用旧文本 |
| ④ | 分集断点 | 开了自动续集时 | 报错，可重试 |
| ⑤ | 字幕语义切分（两层） | **配音完成后** | 回退机械切法 |
| ⑥ | 背景音乐推荐 | 没手选 BGM 时 | 不选 BGM |

共同纪律：**模型只出指令/断点/映射，落地一律由代码确定性执行**，
并且每一处都有逐字校验和回退路径。
