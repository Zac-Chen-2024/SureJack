## 1. 根因:两个状态机都没有被真正设计过

review 里 12 条问题,**9 条源自这两处**:

### 根因 A —— 服务端:成片文件的"身份"是随机的

`deliverFilm()` 用 `randomUUID()` 给成片起名(`deliver-a1b2c3d4.mp4`)。
于是**文件本身不携带任何身份信息**——光看盘上一个 `deliver-*.mp4`,
无法判断它属于哪套参数、是否完整、还有没有人要。

唯一知道这些的是**内存里的 `DownloadPrep`**,而进程一重启就没了。
既然重启后无法分辨"有用的"和"垃圾",开机清扫就只能**一律删掉**——
这正是今天误删她那份 480MB 成片的原因。

> 注释里写着"开机时一定没有正在进行的下载,删了不会误伤"。
> 这句话在**主动重启服务改配置**时是错的,而我们今天就这么干了。

### 根因 B —— 客户端:一条下载的状态散在六个地方

```
STATE(内存 Map) + SharedPreferences(磁盘) + ACTIVE(Set)
+ PAUSED(Set) + CANCELLED(Set) + downloadIds(List)
```

六份状态没有单一真相来源,而且**下载的身份是 `System.currentTimeMillis()`**——
每次点下载都是一个新 id。于是:

- 删除只清内存 → 磁盘里那份复活(review #2)
- 进程被杀重投 + restore 复活 → 同一条片子两条记录(review #8)
- 暂停在工作线程里死等 → 占死单线程池(review #1)
- 生命周期靠状态字符串判断 → 僵尸记录让服务永不退出(review #6)

## 2. 设计一:成片文件的生命周期

### 你定的规则

> **没有下载的文件就一直保持好储存,直到下载了再清除。**

### 做法:让文件名携带身份

把随机串换成**参数指纹**:

```
deliver-<fp>.partial.mp4   ← 正在混，未完成
deliver-<fp>.mp4           ← 混好了，待取
```

`fp = sha256(master指纹 + voicePath + voiceGain + bgmPath + bgmVolume
             + coverTitle + aspect).slice(0, 8)`

这一个改动同时解决四件事:

| 好处 | 说明 |
|---|---|
| **重启后认得出来** | 扫到 `deliver-<fp>.mp4`,拿当前参数算一遍 fp,**对得上就是有效的待取成片**,直接登记进 `DownloadPrep`,不用重混 |
| **参数变了自然过期** | 用户调了音量 → fp 变 → 旧文件对不上 → 明确删掉(而不是稀里糊涂留着) |
| **半成品一眼可辨** | 混音写 `.partial.mp4`,完成后 `rename`(原子操作)。**只要 `deliver-<fp>.mp4` 存在就一定完整** |
| **天然去重** | 同一条片子重复请求 → 同一个文件名 → 不会混出两份 |

> ⚠️ 原来用随机串的理由是"两个请求同时下载时不互相覆盖"。
> 改成确定性文件名之后,这个保护由三层接管:`DownloadPrep` 的并发去重、
> 服务端的单流守卫、以及 `.partial` → `rename` 的原子性。**不会退化。**

### 删除时机:收敛成三条,没有 TTL

| 时机 | 说明 |
|---|---|
| ① **下载真正完成** | 传到最后一个字节 → 删。已实现 |
| ② **参数不匹配** | fp 对不上 → 这份已经没人要了 → 删 |
| ③ **项目被删除** | 跟着项目一起走 |

**去掉现在那条 6 小时 TTL** —— 它和"没下载就一直保留"直接冲突。

**开机清扫改成只删垃圾**:`*.partial.mp4`、`*.mixed.mp4`、`*.cover.mp4`,
以及 fp 对不上的旧成片。**完整且匹配的一律保留并 adopt。**

### 磁盘兜底(必须有,否则迟早撑爆)

去掉 TTL 之后,每个"合成好但没下载"的项目会常驻一份约等于母带大小的成片
(实测 480MB)。所以要加一条**低水位保护**:

> 磁盘可用空间低于 **5GB** 时,按"最久没被访问"的顺序删待取成片,
> 直到回到 8GB 以上。删之前记日志说明删了谁。

这样既满足"一直保留",又不会在盘满时把整个服务拖垮
(磁盘满的症状是 502,和下载看着毫无关系——这个坑踩过)。

### 与归档的关系(已确认无冲突)

归档删的是 `master.mp4` / `bg-track.mp4` / `preview/`,**不碰 deliver**。
但有一处要改:

> 现在 `/film/download` 在没有内存记录时会去查 `master.mp4`,
> 不在就回 409「画面还没合好」。
> **改成:先看盘上有没有匹配的待取成片,有就直接传,不依赖 master。**

否则"归档过的项目 + 有待取成片"会下载失败——而那份成片明明是完整的。

## 3. 设计二:安卓下载记录的状态机

### 一条下载 = 一条记录,身份是 projectId

```java
class Download {
    String projectId;    // ← 稳定身份，不再用时间戳
    String title;
    String url;          // 可由 projectId 推导，存着省事
    String cookie;       // 通知栏点「继续」时 Activity 可能不在
    long total, done;
    Status status;       // RUNNING | RECONNECTING | PAUSED | DONE | FAILED
    String error;        // FAILED 时必须有，且要落盘
}

enum Status { RUNNING, RECONNECTING, PAUSED, DONE, FAILED }
```

- **单一真相来源 = 磁盘**(SharedPreferences 里的 JSON),内存只是镜像
- 每次状态转换**立即落盘**;进度节流到每秒一次
- `ACTIVE` / `PAUSED` / `CANCELLED` 三个 Set **全部并进 `status`**
- key 是 `projectId` → **天然去重**,不需要按文件名去重

### 状态转换图

```
        点下载
          ↓
      RUNNING ──网络错误──→ RECONNECTING ──退避后──→ RUNNING
          │                      │
          │                      └──连续20次零进展──→ FAILED
          │
          ├──用户暂停──→ PAUSED ──点继续──→ RUNNING
          │              （线程退出，锁释放）
          │
          ├──致命错误──→ FAILED（401/403/404/磁盘满，带原因）
          │
          └──传完──────→ DONE（删记录、删 .part）
```

### 关键改动逐条

| # | 改动 | 解决 review 第几条 |
|---|---|---|
| 1 | **暂停让 worker 退出线程**,不再 `while(sleep)` 死等;锁随线程退出释放 | #1(占死线程 + 整夜耗电) |
| 2 | **取消/删除同时清内存和磁盘** | #2(删了会复活) |
| 3 | **HTTP 状态码单独传递**,不再从异常消息里 `contains` 猜;5xx/超时→可重连,401/403/404/410→致命,416→从 0 重下 | #3(方向反了,越接近下完越容易前功尽弃) |
| 4 | **每条下载一个通知 id**;服务停止时 `STOP_FOREGROUND_REMOVE` 明确移除 | #4(划不掉的僵尸通知) |
| 5 | **连续 20 次零进展才放弃**(有进展就清零);磁盘满(ENOSPC)直接致命 | #5(磁盘满时永远"重连中") |
| 6 | **空闲判定基于"有没有活着的 worker"**,不看状态字符串 | #6(僵尸记录让服务永不退出) |
| 7 | **`Service.onCreate` 也先 restore 再 persist**;并且改成**按记录合并**而不是整体覆写 | #7(服务被系统重启时抹掉其他记录) |
| 8 | key 换成 projectId → 重投和 restore 落在同一条记录上 | #8(每杀一次进程多攒一条幽灵) |
| 9 | **status 和 error 如实落盘**,restore 时 FAILED 仍是 FAILED | #9(致命失败伪装成"已暂停") |
| 10 | 悬浮下载角标**挪到不与「下载视频」按钮重叠的位置** | #10(按钮被劫持) |
| 11 | `▶`/`⏸` 换成 `IconPlay`/`IconPause` | #11(违反 SVG 图标规矩) |
| 12 | `esc/unesc` 换成复用已有的 `jsonStr()` | #12(含 `\p` 的标题会损坏) |

### 「继续」按钮的完整设计

今天她点了没反应,是因为 `s.url == null` 时那段逻辑**静默什么都不做**。
新设计:

```
点「继续」
  ↓
该 projectId 有活着的 worker？
  ├─ 有 → 只清 PAUSED 标记，worker 自己会继续
  └─ 无 → 起一个新 worker（url 从记录取，取不到就用 projectId 现推）
            ↓
        cookie 还有效？
          ├─ 有效 → 从 .part 的断点接着传
          └─ 401  → FAILED「登录过期，请重新打开 App」（而不是装死）
```

**任何一条路径都不能是"什么都不发生"** —— 要么开始传,要么给出明确的失败原因。

## 5. 实施顺序(分四批,每批可独立上线和回滚)

### 第一批:服务端成片生命周期 ⭐ 最高优先

**为什么排第一**:它不需要她更新 App,今天就能生效,而且直接解决
"辛辛苦苦下了一半、服务一重启全没了"这个最伤的问题。

1. `deliverFilm()`:随机串 → 参数指纹;混音写 `.partial.mp4` 后 `rename`
2. `sweepDelivered()`:只删 `.partial` / `.mixed` / `.cover` / fp 对不上的
3. 开机 adopt:扫描待取成片,匹配的登记进 `DownloadPrep`
4. `/film/download`:有待取成片时不再依赖 `master.mp4`
5. 去掉 6 小时 TTL,加低水位 LRU 兜底
6. 测试:新增"重启后待取成片仍在且能直接下载""参数变了旧成片被清理"
   "磁盘低水位时按 LRU 清理"

**验证**:造一份待取成片 → 重启服务 → 文件还在 → 直接下载成功、不重混。

### 第二批:安卓状态机重构

1. 新建 `DownloadStore`(磁盘为唯一真相),`Download` 记录以 projectId 为 key
2. 六份状态合并进 `status`
3. 暂停改成线程退出;继续改成重新入队
4. HTTP 状态码单独传递,重连/致命分类修正
5. 通知 id 按下载区分,服务停止时明确移除
6. `Service.onCreate` 也 restore

**验证**:装 2.8.0 → 下一半 → 强杀 App → 重开 → 下载栏有记录且状态正确 →
点继续 → 从断点接上。再测:暂停 A 之后能正常下 B。

### 第三批:界面

1. 悬浮角标位置(#10)
2. `IconPlay`/`IconPause`(#11)
3. 四种状态的文案(正在下载 / 断线了正在重连 / 已暂停 / 失败+原因)

### 第四批:收尾

1. `esc/unesc` → `jsonStr()`(#12)
2. persist 和通知的节流(每秒重建通知渠道和 PendingIntent 的效率问题)
3. 更新 `docs/pipeline.md` 里下载那一节
