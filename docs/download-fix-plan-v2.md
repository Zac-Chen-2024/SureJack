## 1. 产物生命周期(全局设计的地基)

一条片子在盘上有四样东西,**层层叠上去的**:

```
素材库（13GB，全局共享，永不属于某个项目）
   │  按【排布清单】挑片段首尾相接，凑够配音时长
   ↓
① 背景轨 bg-track.mp4   385 MB   纯画面，无字幕无声音
   │  libass 把字幕烧进画面像素
   ↓
② 母带 master.mp4       449 MB   有字幕的画面，【无声】
   │
   ├──→ ③ 预览 preview/  ~70 MB   母带压到 540×960/0.9Mbps 切 6 秒一段
   │
   │  下载那一刻才混音 + 接封面
   ↓
④ 成片 deliver-<fp>.mp4 458 MB   封面 + 画面 + 配音 + BGM ← 用户要的东西
```

### 各自的删除时机(**这一节是新的**)

| 产物 | 什么时候删 | 为什么 |
|---|---|---|
| **① 背景轨** | **母带烧录成功的那一刻** | 纯中间产物,母带烧完再没人读它。排布清单已物化进库,重拼是确定性的(逐帧一样)。⚠️ **必须是"成功之后"**,不能提前——烧录中途失败重试要能直接复用它,否则每次失败都得从重拼开始 |
| **② 母带** | 归档时(下载完成后满 2 小时) | 可重算,但重算要十几分钟,所以留一段时间给用户反复看 |
| **③ 预览** | 跟着母带一起 | 它是从母带算的,母带都没了它更没意义 |
| **④ 成片** | **下载真正完成的那一刻** | 用户已经拿走了。重混只要十几秒,不值得留 458MB。✅ 已实现 |
| 配音 voice.mp3 | **永不删** | 重配音会拿到不同的词级时间戳,字幕全部错位。才 6MB |

**这一刀(①)每条项目立省 385MB,而且立刻省、不用等归档。**
现在那条项目盘上 904MB,其中 385MB 就是它。

### 磁盘模型因此变成

| 阶段 | 盘上留什么 | 大小 |
|---|---|---|
| 合成完成 | 母带 + 预览 + 配音 + 索引 | **~520 MB** |
| 到点归档 | 配音 + 索引 | **~9 MB** |
| 下载那一刻 | 上面的 + 临时成片 | +458 MB(传完即删) |

中间态那 385MB 彻底消失。

## 2. 成片文件的身份:参数指纹

### 你定的规则

> **没有下载的成片就一直保持好储存,直到下载了再清除。**

### 问题:现在文件名是随机的

`deliverFilm()` 用 `randomUUID()` 起名(`deliver-a1b2c3d4.mp4`)。文件**不携带任何身份信息**——
光看盘上一个 `deliver-*.mp4`,无法判断它属于哪套参数、是否完整、还有没有人要。
唯一知道的是内存里的 `DownloadPrep`,进程一重启就没了。

既然重启后分辨不出"有用的"和"垃圾",开机清扫只能**一律删** ——
**这就是 18:12 误删用户正在下载的那份 480MB 的原因**(review #13)。

### 解法:文件名 = 参数指纹

```
deliver-<fp>.partial.mp4   ← 正在混，未完成
deliver-<fp>.mp4           ← 混好了，待取（rename 是原子的）
```

```
fp = sha256(母带指纹 + voicePath + voiceGain + bgmPath + bgmVolume
            + coverTitle + aspect).slice(0, 8)
```

一个改动同时解决四件事:

| 好处 | 说明 |
|---|---|
| **重启后认得出来** | 拿当前参数算一遍 fp,对得上就是有效的待取成片,直接登记进 `DownloadPrep`,**不用重混** |
| **参数变了自然过期** | fp 对不上 → 明确清理,而不是稀里糊涂留着 |
| **半成品一眼可辨** | 只要 `deliver-<fp>.mp4` 存在就一定完整 |
| **天然去重** | 同一条片子重复请求 → 同一个文件名 |

> ⚠️ 随机串原本是为了"两个请求同时下载不互相覆盖"。改成确定性文件名后,
> 这个保护由三层接管:`DownloadPrep` 并发去重、服务端单流守卫、
> `.partial` → `rename` 的原子性。**不会退化。**

### 与"音量自动保存"的关系(**修正:这里 v2 初稿写重了**)

音量滑块是**拖动即保存**的:300ms 防抖 → `PATCH` 写进 `voice_gain` / `bgm_volume`。

但**指纹只在两个时刻被查:请求下载时、开机扫描时**。拖音量本身
【什么都不触发】——不混音、不比对、不删文件。所以不存在"拖着玩两下就把
混好的成片弄没了"这回事。

唯一的真实后果:**手上有一份没下载的成片,之后改了音量,再点下载时会发现
指纹对不上 → 重混一次(十几秒)→ 删掉旧的。** 这是正确行为——
不然她拿到的是旧音量的片子。

### 删除时机收敛成三条,**没有 TTL**

① 下载真正完成 ② 请求下载时发现 fp 不匹配 ③ 项目被删除

**去掉现在那条 6 小时 TTL** —— 它和"没下载就一直保留"直接冲突。

### 开机清扫改成只删垃圾

只删 `*.partial.mp4` / `*.mixed.mp4` / `*.cover.mp4` / fp 对不上的旧成片。
**完整且匹配的一律保留并 adopt 进 `DownloadPrep`。**

### 与归档的关系

归档删母带,**不碰成片**。但有一处要改:

> `/film/download` 现在没有内存记录时会去查 `master.mp4`,不在就回 409。
> **改成:先看盘上有没有匹配的待取成片,有就直接传,不依赖 master。**

否则"归档过 + 有待取成片"会下载失败,而那份成片明明是完整的。

## 3. 磁盘不够时:两步回收(**替换 v1 的 LRU 方案**)

**核心原则:磁盘压力只用"可重算的东西"化解,永远不动用户还没拿到手的成品。**

### 第一步 —— 提前归档

找"**已经下载过、但还没到两小时归档阈值**"的项目,提前归档。
判据用现有字段就够,**不需要加列**:

```sql
downloadedAt != ''   AND   archivedAt = ''
```

> ⚠️ 这一步的正确性**依赖 `downloadedAt` 的新语义**(只有真正传完最后一个字节才写)。
> 今天已经修好。要是还是老的"开始传就写",这一步会把用户根本没下成的项目归档掉。

每条能腾约 **520MB**(母带 + 预览)。

### 第二步 —— 提醒用户下载

如果没有可提前归档的,磁盘还是不够,说明空间被"合成好了但用户还没下载"的片子占着。
**这时候不能删** —— 那是他要的东西。改成:

> **告诉用户:先把《XX》下载了,腾出空间才能继续合成。**

用户下完 → **自动归档那一条** → 空间释放 → **被卡住的合成自动继续**,不用他再点一次。

### 需要的设计

**① 新模块 `src/compose/disk-guard.ts`**

现在磁盘检查**只在下载那条路上有**(`download-queue.ts` 的 `SPACE_FACTOR`),
**合成这条路完全没有预检** —— 这是缺口。新模块提供:

| 函数 | 职责 |
|---|---|
| `freeBytes()` | 查可用空间 |
| `reclaimable()` | 列出"已下载未归档"的项目及各自能腾多少 |
| `reclaim(need)` | 按需提前归档直到够用;返回腾了多少、归档了谁 |
| `blockedBy()` | 腾不出来时,返回"卡住合成的是哪几条待下载的片子" |

**② `export_jobs` 加第五种状态**

```
blocked_disk  —— 磁盘不足，等用户下载腾空间
```

**不能复用 `failed`**:失败是终态、要用户手动重试;而这里是**可自愈的等待** ——
用户一下载完就该自己接上。

附带信息(存进 `error` 字段的结构化 JSON,不用加表):还差多少 GB、建议下载哪条(项目 id + 名字)。

**③ 三个触发点**

| 时机 | 做什么 |
|---|---|
| **合成入队前** | 预检 → 不够先 `reclaim()` → 还不够置 `blocked_disk` + 建议下载的项目 |
| **下载完成那一刻** | 磁盘紧张时**立即归档这一条**(不等两小时)→ **唤醒被 `blocked_disk` 卡住的任务** |
| **归档定时扫描** | 保持现状(2 小时),它是常态回收;`reclaim` 是应急回收 |

**④ 前端一种新状态**

> **等待空间** · 磁盘不够了,先把《周周隐婚》下载完就能继续 → [去下载]

## 4. 安卓下载记录的状态机

> **详细方案见 `docs/android-download-refactor.md`** —— 这里只留骨架。

### 根因:一条下载的状态散在六个地方

```
STATE(内存) + SharedPreferences(磁盘) + ACTIVE + PAUSED + CANCELLED + downloadIds
```

六份状态没有单一真相来源,而且**身份是 `System.currentTimeMillis()`** ——
每次点下载都是新 id。review #1/#2/#6/#7/#8/#9 全部由此而来。

### 一条下载 = 一条记录,key 是 projectId

```java
class Download {
    String projectId;   // ← 稳定身份，不再是时间戳
    String title, url, cookie;
    long total, done;
    Status status;      // RUNNING | RECONNECTING | PAUSED | DONE | FAILED
    String error;       // FAILED 时必须有，且要落盘
}
```

- **单一真相来源 = 磁盘**,内存只是镜像
- 状态转换立即落盘;进度节流每秒一次
- 三个 Set 全部并进 `status`
- key 是 projectId → **天然去重**

```
      点下载
        ↓
    RUNNING ──网络错误──→ RECONNECTING ──退避──→ RUNNING
        │                      └──连续20次零进展──→ FAILED
        ├──用户暂停──→ PAUSED（线程退出，锁释放）──点继续──→ RUNNING
        ├──致命错误──→ FAILED（401/403/404/磁盘满，带原因）
        └──传完──────→ DONE（删记录、删 .part）
```

### 逐条对应 review

| # | 改动 | 修复 |
|---|---|---|
| 1 | 暂停让 worker **退出线程**,锁随之释放 | #1 占死线程 + 整夜耗电 |
| 2 | 取消/删除**同时清内存和磁盘** | #2 删了会复活 |
| 3 | **HTTP 状态码单独传递**,不再从异常消息 `contains` 猜。5xx/超时→可重连,401/403/404/410→致命,416→从 0 重下 | #3 方向反了 |
| 4 | 每条下载一个通知 id;服务停止 `STOP_FOREGROUND_REMOVE` | #4 僵尸通知 |
| 5 | **连续 20 次零进展**才放弃(有进展清零);ENOSPC 直接致命 | #5 磁盘满永远"重连中" |
| 6 | 空闲判定基于"**有没有活着的 worker**",不看状态字符串 | #6 服务永不退出 |
| 7 | `Service.onCreate` 也先 restore;persist 改**按记录合并** | #7 抹掉其他记录 |
| 8 | key 换 projectId | #8 每杀一次攒一条幽灵 |
| 9 | status/error **如实落盘**,FAILED 恢复后仍是 FAILED | #9 失败伪装成已暂停 |
| 10 | 悬浮角标挪位 | #10 按钮被劫持 |
| 11 | `IconPlay`/`IconPause` 替换文本字形 | #11 违反 SVG 规矩 |
| 12 | `esc/unesc` → 复用 `jsonStr()` | #12 含 `\p` 损坏 |
| 14 | 「继续」**任何路径都不能什么都不发生** | #14 静默失败 |

### 「继续」的完整设计

```
点「继续」
  ↓
该 projectId 有活着的 worker？
  ├─ 有 → 清 PAUSED 标记，worker 自己继续
  └─ 无 → 起新 worker（url 从记录取，取不到就用 projectId 现推）
            ↓
        cookie 还有效？
          ├─ 有效 → 从 .part 断点接着传
          └─ 401  → FAILED「登录过期，请重新打开 App」
```

**每一条路径要么开始传,要么给出明确失败原因。**

## 5. 全局冲突检查

| 关注点 | 结论 |
|---|---|
| 旧版本 App 会坏吗 | 不会。服务端 URL 和响应语义不变 |
| 要发版吗 | 安卓改动要 **2.8.0**;服务端改动不需要她更新 |
| 背景轨删除 vs 合成重试 | **必须在母带烧录成功后才删**,否则中途失败重试要从重拼开始 |
| 背景轨删除 vs 改字幕/换开头 | 重烧母带要先重拼背景轨,多几分钟。用户已确认"这个一般不会调整",可接受 |
| 归档 vs 待取成片 | 归档不碰成片;但 `/film/download` 要改成有成片时不依赖 master |
| `downloadedAt` 语义 | 保持"只在真正下载完成时写"。**两步回收的第一步依赖它** |
| 音量自动保存 vs 成片指纹 | 拖滑块会让待取成片失效 → 清理时机要克制(只在请求下载时和开机时) |
| 现有 974 个测试 | `sweepDelivered` 目前没有专门测试;`export-formula.test.ts` 三条下载测试会受语义影响,要跟着改 |

## 6. 实施顺序(四批,各自可独立上线回滚)

### 第一批:服务端产物生命周期 ⭐ 最高优先

**不需要她更新 App,今天就能生效。**

1. **母带烧成后立即删背景轨**(每条立省 385MB)
2. `deliverFilm()`:随机串 → 参数指纹;写 `.partial` 后 `rename`
3. `sweepDelivered()`:只删垃圾和 fp 不匹配的
4. 开机 adopt:待取成片登记进 `DownloadPrep`
5. `/film/download`:有待取成片时不依赖 master
6. 去掉 6 小时 TTL
7. 测试:重启后待取成片仍在且能直接下载、参数变了才清理、背景轨在母带成功后才删

### 第二批:磁盘两步回收

1. `disk-guard.ts`
2. `export_jobs` 加 `blocked_disk`
3. 三个触发点接线
4. 前端「等待空间」状态 + [去下载] 引导

### 第三批:安卓状态机重构(发 2.8.0)

**建议分两步**:先做"磁盘为唯一真相 + projectId 为 key"(修 #2/#7/#8/#9),
验证过再做暂停/重连改造(#1/#3/#5)。

### 第四批:界面 + 收尾

#10 角标位置、#11 SVG 图标、#12 `jsonStr`、节流优化、更新 `docs/pipeline.md`
